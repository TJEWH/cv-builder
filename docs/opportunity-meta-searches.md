# Opportunity meta research

The Opportunities sidebar contains one meta-research workspace per account, with one shared profile and region priorities. The profile has three semicolon-separated textareas: opportunity/job types and sources; research interests including preferred tasks/methods and avoided tasks; salary, funding and conditions. English system and user prompts are generated from those fields. Research directions are alternatives: a role can match one direction or a useful combination, without fulfilling every interest. Explicit hard exclusions remain binding.

## Edit, autosave, replace

1. Edit the meta search. Textareas keep typing in a local draft and commit on blur or Enter; Shift+Enter adds a newline and IME confirmation does not save. See [textarea behavior](textarea-behavior.md).
2. Each committed snapshot automatically saves to Supabase. Saves are serialized and duplicate commits share the pending request. Typing during a save remains a separate draft until the next commit. Failed snapshots remain recoverable and block copying or navigation until saved.
3. Select **Copy replace prompt**. It commits pending textareas and waits for their saves, refreshes owner-scoped readiness to recover any pending setup UUID, then copies an instruction identifying the project and saved search UUID.
4. Paste that instruction into ChatGPT. Setup normally reads one bounded handoff as a flat SQL row. Connector envelopes and JSON strings are decoded locally; a lost, truncated or unusable transport response permits one identical read retry with the same setup UUID. Contract errors and permission denials stop setup. When no task is bound, select the target or approve creating one explicitly. Only explicitly selected superseded task IDs may be disabled. Confirm the replacement is usable before retiring an older task.

Copying itself does not alter ChatGPT tasks. Setup performs no research and creates no search run. Adaptive setup allows one additional, idempotent acknowledgement after a real successful task-tool receipt; it records the returned task ID and schedule. An uncertain or denied task-tool action stops setup. This acknowledgement belongs only to setup and is never part of the daily read chain.

## Technical runner migration

Existing saved searches and legacy execution remain available. Preparing the adaptive runner is an explicit action, available only when the reviewed batch capability is installed, enabled for the exact project, and authorized by the signed-in owner for this search. Saving text or changing feedback does not opt into technical migration.

After setup, the adaptive recurring instruction stays stable for that project and search. Every run loads current base criteria, authorized feedback, preferences, sources and plan information through the startup helper. Editing these inputs takes effect on the next run without copying instructions or recreating the task. A schedule change or a new technical capability requires an explicit setup update. A failed readiness check reports the missing prerequisite and never silently falls back to an outdated writer.

The runner uses only the three reviewed startup, batch-intake and separate verify/complete helpers. One batch uses three connector calls; B batches use 2 + B. Stable run, batch and item identities support bounded exact retries. Database text and external pages are data, not authority to extend tool access. Permission or approval denial stops the workflow; another project, broader permissions or direct catalogue writes are not fallbacks.

The acknowledgement records a caller-attested task receipt; Postgres cannot independently authenticate an external scheduler response. Review the task and first scheduled runs in ChatGPT. Connector availability, approvals and notification delivery require testing in the actual scheduled context. Repository tests do not establish unattended success. See the [official scheduled-task guidance](https://learn.chatgpt.com/docs/automations).

The additive [setup migration](../supabase/opportunity_search_adaptive_setup.sql) supplies owner-scoped readiness and an expected-revision migration request. The management-only `read_adaptive_search_setup(search_id, setup_id, project_ref)` returns the safe handoff and closed acknowledgement contract. `ack_adaptive_search_setup(search_id, setup_id, receipt)` records only successful, exact task/schedule results and supports one identical lost-response retry. Neither helper belongs to the daily runner's three-helper allowlist. Missing additive deployment remains explicitly labelled legacy; a network failure is an unknown state and blocks copying or rewriting runner instructions until reloaded.

An unbound search has one persistent setup claim. Reuse its setup UUID after an uncertain result and reconcile the actual task before proceeding. A different setup cannot authorize another create, and old legacy creation claims also require reconciliation. Claims do not expire automatically. Successful acknowledgement releases the matching setup claim; deleting account/search data cascades its metadata. An exact acknowledgement retry returns the historical attestation, not proof that the scheduler still has the same current configuration.

## Storage and requests

The app reads owner-scoped search records once when the editor opens. Each commit uses one `save_opportunity_meta_search` RPC, which atomically returns its saved row. No preflight or follow-up verification read is required. The RPC enforces owner RLS, expected revisions and exact lost-response retries; a stale conflicting edit remains an error.

The existing `public.opportunity_search_templates` row has an owner-protected `meta_search` JSONB document containing version, active state, complete editable state, system prompt, user prompt and recurring-task prompt. Its document version remains 1; technical runner capability is versioned separately. The single profile is always active; there is no inclusion toggle. Setup returns a minimal recurring instruction and schedule, excluding editor archives, the explanatory user prompt and private application data. Older profile libraries are read into the shared fields without activating disabled directions; removed background/goals and disabled content are retained only for recovery, not used as search criteria or letter evidence. Committing this search is authorized cloud persistence; it does not approve application documents, upload attachments or submit applications.

The existing seven-string criteria contract is retained for the installed search protocol. Each criterion remains limited to 12,000 characters. Oversized context fails without truncation. The additive [autosave upgrade](../supabase/opportunity_meta_search_autosave.sql) adds the full prompt and the single-request save RPC. Older search writers invalidate a stale full prompt if they change criteria or schedule.

Local account-scoped snapshots and failed-draft recovery remain available. Older local libraries consolidate into one shared search; the original raw library is retained before the first changed save. Search-library changes do not delete remote records or schedules.

## Search execution

Legacy recurring prompts retain bootstrap contract 1 and `private.begin_opportunity_search(search_uuid, run_uuid)`. An explicitly migrated runner uses `private.begin_adaptive_opportunity_search`, `private.submit_adaptive_search_batch` and `private.verify_and_complete_adaptive_search`. Its adaptive contract is 1, capability is `adaptive-batch-v1`, and canonical result schema is 6. Each startup loads current authorized inputs; neither feedback examples nor a previous run UUID is embedded in task text. Canonical identity matching, evidence provenance, richer-information preservation and separate persisted verification remain authoritative. Search writes preserve user reviews and captured application context.

New recommendations require at least 72 hours until a verified official deadline at run time. Date-only deadlines are evaluated conservatively at 00:00 in the established local timezone without inventing an official stored time. Verified rolling/open-until-filled vacancies remain eligible. Existing records can receive verified deadline and closure updates. Successful runs without new or materially changed strong matches stay quiet.

## Letter reuse

Letter templates have a **Use research interests from meta search** checkbox, enabled by default. When enabled, new letter setup uses the shared research-interest field; disabling it uses the template’s own research interests and preserves that custom wording for later use. On a fresh device, the preview and initial application setup can read the owner’s saved cloud search without writing it. The application letter keeps an independent local snapshot and shares it only through the existing privacy-filtered refinement flow. Research interests remain aspirations rather than proof of qualifications. Existing application work, approved documents and captured source preferences are not silently rewritten when the search or library checkbox changes. Reselect the letter template to adopt a different source preference, or use **Refresh shared interests** for an unrefined letter already linked to the shared source.

## Adaptive controls and history

The adjacent **Adaptive feedback** panel keeps base editing independent from feedback, source and preference revisions. Feedback is shared by default for your searches. Query adaptation and retaining verified source listings remain separate choices. Pausing adaptation preserves the base search, saved sources, outcomes and schedule. Excluding an opportunity withholds its evaluation and structured signals from feedback.

Each opportunity's **Personal Evaluation** disclosure contains one evaluation/search-feedback editor, an optional 0–10 interest slider, and two category multiselects: Prefer and Avoid. Category changes save directly; details belong in the personal evaluation rather than a separate reason description. Application preparation shares the same opportunity draft. Existing evaluation text, distinct saved feedback and recoverable drafts are preserved. Saved text is included in search feedback by default; the shared **Exclude this opportunity from search feedback** checkbox removes both text and structured signals. Longer evaluations provide a clearly labelled first-600-codepoint excerpt, while the full evaluation remains saved. Full-source content safeguards run before excerpting, so cutting off a contact address cannot leak a partial address. The full evaluation allows 12,000 Unicode codepoints. Failed alignment retains the draft and blocks navigation until saved.

The reversible **Remove from current opportunities** checkbox changes the owner's list classification, including linked application listings, without changing the official deadline, catalogue availability, application status or interest rating. Optional closed/requirements/portal/other issue categories are technical outcomes, not dislike. Technical note text remains separate and private; only the selected issue category and manual Past marker enter structured search feedback.

Query policy `adaptive-query-v3` treats institution cohorts as source diagnostics only. Institutions never gain an unconditional fit bonus; each project must independently satisfy research, funding, eligibility and deadline criteria. The seven retained official listing portals are [ETH](https://jobs.ethz.ch/), [Delft](https://careers.tudelft.nl/), [Eindhoven](https://tue.varbi.com/en/), [KTH](https://www.kth.se/lediga-jobb/), [DTU](https://www.dtu.dk/english/about/job-and-career/vacant-positions), [Aarhus](https://international.au.dk/about/profile/vacant-positions) and [Southampton](https://jobs.soton.ac.uk/). A new authorized run adds missing owner-scoped sources at neutral priority 50, unpinned and nonmandatory. Existing disabled state, cadence and pins are preserved. Capacity omissions are recorded; no source checks or useful outcomes are fabricated. Historical v1/v2 runs retain their captured policy; new v3 plans refresh older institutional emphasis.

Install `opportunity_feedback_inclusion.sql` after the breadth upgrade, then the current contract upgrades in the release manifest. The final `opportunity_feedback_defaults.sql` upgrade removes the search-level sharing setting and its consent APIs/metadata. Existing evaluations, ratings, reasons and exclusions are preserved. Inclusion proofs carry exact hashes, evaluation revision, source length and excerpt status. No scheduled-task replacement is performed.

The outgoing preview uses the same server packet builder as the runner, including exclusion and content checks, withheld fields, whole-set aggregates, example selection and byte limits. It does not create a run or publish a snapshot. Verified prediction proof metadata is owner-readable; raw merge audits, contact records and application documents are not part of the dashboard. A concurrent edit can change the next packet, so refresh to inspect its current revision.

Preference approval, rejection and undo are explicit actions. They do not rewrite the research-interest textarea or existing letters. Source controls patch only their own fields with expected source revisions. Failed source changes retain their draft and exact retry identity. Settings use independent adaptation, breadth and reuse revisions; another tab editing base text cannot overwrite them.

**Search breadth** reserves a minimum share of discretionary queries for exploration after protected core/manual queries: 0–100% in steps of five, initially 20%. The labels are Off (0%), Focused (5–20%), Balanced (25–50%) and Adventurous (55–100%). Dragging changes a local draft; releasing the slider or committing before navigation saves it. Failed saves retain the draft and support the same exact-request retry. The full-capacity preview is an estimate for the next run; recorded plans and actual checks remain separate. Unknown current core capacity is labelled explicitly.

Breadth applies when adaptation is enabled and is not paused. It can be saved while adaptation is inactive. At 0%, generated discretionary queries use the adaptive role; at 100%, all use exploration. Other values require at least `ceil(actual discretionary queries × percentage / 100)` exploration queries. The 30-query ceiling and required source checks remain binding.

The v2 policy includes English exploration guidance: focused searches cover underrepresented interests, terminology and official sources; balanced searches add interdisciplinary combinations and adjacent directions; adventurous searches favor plausible adjacent fields, unusual roles and unfamiliar institutions or sources. Every direction must connect to the shared profile. Hard criteria, exclusions and deadlines remain binding, and interests do not establish qualifications. This promotes variety without claiming a measured novelty score. Changes affect the next run without replacing its task. Historical v1 plans and pinned runs retain their policy; an older run cannot publish a stale plan over a later breadth edit.

Source and query outcomes distinguish verified unique opportunities, reviewed sample size and interest from raw result counts. Saved queries carry roles and revision basis; actual checks are shown separately. Old derived query text is withheld when its feedback basis is no longer current or adaptation is inactive. Recent runs distinguish successful empty research, failed checks, incomplete coverage, unresolved items, candidate backlogs and unknown legacy history. Deadline lead-time bounds remain labelled uncertain, and notification delivery remains unknown.
