# Opportunity meta research

The Opportunities sidebar includes one meta-research workspace per account, with shared professional context, research interests, an editable English user prompt and multiple professional profiles. A search matches any enabled profile. Disabling a profile excludes its context from copied search prompts and cloud publication; it can still be explicitly selected as motivation-letter context. Explanations use the shared hover/focus hint buttons, and the editor body scrolls independently on desktop.

The search saves locally under the signed-in account. Textarea drafts commit on blur or Enter, following [the shared textarea behavior](textarea-behavior.md). Import restores the single local search while retaining only its existing local publication binding; another account's search or schedule identity is never imported. Backups contain private context. Older libraries with multiple instances are consolidated into profiles within one search; the original raw library is retained in an account-scoped recovery key before its first changed save. No remote records or schedules are deleted by this migration.

**Publish** is an explicit disclosure action. It publishes the shared context, editable strategy, enabled profiles and requested daily time to the owner's existing Supabase search-template record. An unlinked local search reuses the owner's latest saved search when available. Typing, committing a textarea or selecting letter context does not publish or schedule anything. Published context is available to administrative ChatGPT research tooling in the connected project; it is not an anonymized CV projection.

**Copy daily search prompt** requires the current template to be published. Paste it into ChatGPT with access to the connected Supabase tooling and ChatGPT scheduling. Copying alone does not create a task. Each run reads the latest explicitly published strategy and current installed research protocol. Later local edits take effect after publication; schedule changes are applied by the next successful execution. Importing an older hourly/weekly search leaves its remote record and existing task untouched; explicitly publishing it adopts the daily time shown in this editor.

The separately copied system and user prompts include the exact project and saved search UUID when the current template is published. Each requires the same dynamic bootstrap before execution. Unpublished or stale copies explicitly stop execution and request publication followed by a fresh copy; they never fall back to another search or direct catalogue writes. These individual prompts do not instruct ChatGPT to create or change schedules.

## Existing connected protocol

The deployed `phd-workflow` project already provides `public.opportunity_search_templates`, owner RLS and `save_opportunity_search_template`. The frontend publishes through that RPC with an expected revision, then performs a separate owner-scoped read to verify the saved record. Stable owner/template-derived UUIDs make an initial create retry refer to the same search. Before writing, an owner-scoped read can recover an exact matching payload at the expected revision or its immediate successor when an earlier write response or verification was lost. Different content or a later revision remains a conflict; the frontend never advances over it automatically. Conflicting updates retain the local draft for review.

The existing criteria contract accepts seven string fields: `opportunityTypes`, `topicsAndMethods`, `locationsAndLanguages`, `fundingAndConditions`, `fitAndExclusions`, `sourcesAndQueries` and `researchAndReporting`. Each is limited to 12,000 characters. `fitAndExclusions` contains a versioned, structured meta-search context; `researchAndReporting` holds the shared editable user prompt. Enabled profiles retain their own context, interests and strategy. Oversized combined context fails explicitly without truncation or loss of the local draft.

Generated tasks use bootstrap contract 1 and `private.begin_opportunity_search(search_uuid, run_uuid)` to read the current definition, immutable query revision, protocol text, result schema and schedule binding. The active protocol was verified read-only on 2026-10-28 as `opportunity-search-v1-2026-10-12-normalization-3`; generated tasks deliberately do not freeze that release.

The installed protocol owns query publication, canonical identity matching, field types, source provenance, richer-evidence preservation, 0–10 score validation, per-result submission, separate verification receipts, terminal run verification and bounded recovery. Tasks use those helpers through the currently exposed Supabase connector. They never write the catalogue directly, run schema discovery or apply migrations. Existing reviews and captured application context remain outside search writes.

New results are reported or recommended only with at least 72 hours before their official deadline at the actual run time. A date-only deadline is conservatively evaluated at the start of that date in an established local timezone; this calculation must not invent a stored deadline time. Officially open rolling/open-until-filled vacancies without a fixed date are eligible. Ambiguous deadlines require verification. This filter does not prevent verified catalogue writes under the installed protocol. Existing records can still receive verified deadline and closure updates.

The setup prompt completes and verifies the first search before scheduling. An existing schedule binding identifies the task to update. First-time creation uses `private.claim_opportunity_search_schedule` and confirms only a real tool-returned task ID through `private.confirm_opportunity_search_schedule`. Concurrent setup cannot silently create a replacement. Successful unchanged or empty recurring runs stay quiet; meaningful matches, actionable failures and initial setup return concise evidence-based status.

## Letter reuse

Application preparation explicitly selects a meta search and optional professional profile. This freezes the selected context in the local application letter and preserves privacy filtering in the existing refinement publication flow. Research strategies are not copied as applicant evidence. Interests and possible directions remain distinguishable from qualifications. Editing a library profile does not silently rewrite an application's frozen source or approve its documents.

No database migration is required for this frontend extension on the connected project. Fresh databases that only use the committed general workspace schema do not include the existing search protocol; the UI reports missing search support rather than bypassing it.
